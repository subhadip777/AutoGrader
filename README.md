# AutoGrader: A Rule-Driven Evaluator for C Programs

AutoGrader grades student C programs according to rules the instructor writes in a JSON file.
A teacher creates an assignment from a problem statement and a grading policy, a local LLM
generates test cases, the teacher reviews and accepts them, and the assignment is published.
Students upload a `.c` file; the program is compiled and run in a locked-down Docker sandbox,
checked by one analyzer per metric, and the student gets a weighted grade with a report that
shows the failing inputs, the expected outputs and why.

> The core contract: **the same submission graded under the same rules gets the same grade.**
> Every deterministic metric is reproducible; the two measurement-based ones (LLM readability and
> timing-based complexity) are labelled as such in every report.

## Features

**Teacher**
- Create an assignment: title, problem statement (typed or loaded from `.txt`), grading policy (`.json`),
  optional reference solution (`.c`, never shown to students) and the number of tests
- The policy is validated in the browser and again on the server: weights sum to 1.00, analyzer names
  exist, compiler flags are on an allow-list, limits and the input format are valid
- Test cases are generated by a local LLM (Ollama) through a LangGraph workflow; review, **Regenerate** or **Accept**
- **Publish** locks the assignment (tests, rules and reference become immutable)
- **Delete** an assignment (draft or published). The folder, with its submissions and reports, is moved to
  `data/Trash/<id>-<time>` rather than erased, so it can be restored by moving it back; if students have
  submitted, the teacher must type the assignment ID to confirm. Refused while tests are being generated or
  a submission is being graded
- **Submissions** page: every student's state, grade and flags, the full report, originality matches,
  all attempts, the source, and **Regrade**

**Student**
- See published assignments, read the statement, upload a `.c` file with name and roll number
- Live grading progress, then the grade, a per-metric table, failing tests and counter-tests with
  input / expected / got / why, and suggestions
- Download `report.txt` and `report.json`; resubmit at any time (earlier attempts are kept and listed)

**Grading engine**
- Docker sandbox: no network, read-only root, CPU/memory/process/output/time limits, all capabilities
  dropped but four, student code runs as `nobody`; infinite loops, crashes, fork bombs and output floods are contained
- First pass (compile + smoke run + static sanity); a smoke-run timeout sets `suspected_infinite_loop`
  and skips every execution-based analyzer
- Nine analyzers, a LangGraph grading graph, weighted scoring that never redistributes missing weight,
  JSON + text reports with tool versions, rules hash and a reproducibility fingerprint

## How it works

```
Browser (HTML/CSS/JS, no build step)
        |
        v
FastAPI (one server, port 8000) --- serves frontend/ and /api/...
   |-- agents/testgen.py   LangGraph: generate -> validate -> loop          (Ollama)
   |-- server/jobs.py      grading queue (thread pool, survives restarts by re-queuing)
   '-- agents/grader.py    LangGraph grading graph, in-process
            |
            |-- grading/first_pass.py, grading/analyzers/*   one analyzer per metric
            |-- grading/scoring.py, grading/report.py        weighted grade, reports
            '-- server/sandbox.py --(JSON job on stdin)--> docker run ... autograder-sandbox:2
                                                            '-- sandbox/runner.py (gcc, ASan/UBSan,
                                                                valgrind, cppcheck; runs code as nobody)
        |
        v
data/Assignments/ASG-XXXXXX/...   (plain JSON and text files)
```

**Grading graph** (`backend/agents/grader.py`)

```
validate -> first_pass -+-> correctness -> edge_cases -+-> compiler -> structure -+-> memory -> complexity -+-> review -> aggregate -> report
                        '-> skip_execution ------------'                          '-------------------------'
```

- `validate` re-checks the policy and the tests (a malformed policy can never produce a grade)
- `first_pass` compiles with the execution flags and with each set of warning flags from the rules,
  runs cppcheck, and runs the program once on the first accepted test
- If the program does not compile or the smoke run times out, `skip_execution` records correctness,
  edge cases, memory safety and complexity as **skipped (0)**, and only the source-based analyzers run
- Each stage runs the metrics of the rules whose analyzer belongs to it. A crashing analyzer is recorded
  as `error`, the rest of the graph continues
- `aggregate` builds the flags, `report` computes the grade and writes both reports

## Installation

Requirements: Python 3.11+, Git, Docker (Docker Desktop on Windows/macOS, Docker Engine on Linux),
and optionally Ollama for test generation and the readability review.
gcc, the sanitizers, valgrind and cppcheck do **not** need to be installed on the host: they are in the
sandbox image. lizard is a Python package and comes with `requirements.txt`.

### Windows (PowerShell)

```powershell
git clone https://github.com/subhadip777/AutoGrader.git
cd AutoGrader
copy .env.example .env

python -m venv .venv
.\.venv\Scripts\Activate.ps1          # if blocked: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
python -m pip install -r requirements.txt

# Docker Desktop must be running
docker build -t autograder-sandbox:2 sandbox

# Optional: local LLM (https://ollama.com/download)
ollama pull qwen2.5:3b
```

If the path to the clone is very long and `pip` or `git` fail with "Filename too long", clone to a
short path such as `C:\src\AutoGrader` or run `git config --global core.longpaths true`.

### Linux (bash)

```bash
git clone https://github.com/subhadip777/AutoGrader.git
cd AutoGrader
cp .env.example .env

python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt

# Docker Engine: https://docs.docker.com/engine/install/ ; add yourself to the docker group, then
docker build -t autograder-sandbox:2 sandbox

# Optional: local LLM
curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen2.5:3b
```

`docker compose build sandbox` builds the same image; `docker compose --profile llm up -d` runs Ollama
in a container instead of a local install.

### Configuration (`.env`)

| Variable | Default | Meaning |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Ollama server |
| `OLLAMA_MODEL` | `qwen2.5:3b` | model for test generation and readability (on 8 GB RAM, use 3B or smaller) |
| `AUTOGRADER_SANDBOX` | `docker` | `docker` for real use; `wsl` / `process` only for development (see below) |
| `AUTOGRADER_SANDBOX_IMAGE` | `autograder-sandbox:2` | sandbox image tag |
| `AUTOGRADER_SANDBOX_SLOTS` | `1` | containers allowed at the same time |
| `GRADER_WORKERS` | `1` | submissions graded at the same time |
| `AUTOGRADER_DATA_DIR` | `<repo>/data` | where `Assignments/` is stored |

**Development backends without Docker.** `AUTOGRADER_SANDBOX=wsl` (Windows) runs the same
`sandbox/runner.py` under `wsl -u root`, and `process` (Linux) runs it as a subprocess. Student code
still runs as `nobody` with the same rlimits, but there is **no network or filesystem isolation**, so
these are only for developing and testing with trusted sample programs. They also share one process
table, so run only one AutoGrader process (server or test run) at a time with them. The teacher page shows a
warning banner when one is active. With the default `docker` backend and no Docker, nothing falls
back to the host: submissions are stored and marked "Grading is not available", and the teacher can
regrade them once Docker works. For the WSL backend, gcc and python3 must be installed in the default
distribution (`sudo apt install gcc python3`; add `valgrind cppcheck` to enable those tools).

## Running

```powershell
cd backend
uvicorn server.main:app --port 8000
```

Open <http://localhost:8000> (API docs at <http://localhost:8000/docs>, sandbox status at `/api/health`).

**Demo without Ollama:** `python scripts/seed_demo.py` creates and publishes two sample assignments
with hand-written, checked test cases. Then open the student page and upload any file from
`samples/*/submissions/`.

**Grading from the command line** (the agent without the web app):

```powershell
python scripts/grade.py samples/add_two_integers samples/add_two_integers/submissions/overflow.c
python scripts/grade.py samples/sort_numbers --all     # every sample, reports in samples/sort_numbers/reports/
```

LangGraph Studio is optional and only a debugging aid: `cd backend; langgraph dev` shows the
`testgen` and `grader` graphs.

## Running the tests

```powershell
cd backend
python -m pytest -q                       # everything
python -m pytest tests/unit_tests -q      # no sandbox needed (about 2 s)
```

Execution tests use `AUTOGRADER_SANDBOX` when set; otherwise Docker if its image exists, then WSL on
Windows, then a plain process on Linux. When no backend works they are skipped with the reason.
The network-isolation test only runs with the Docker backend.

The suite covers: policy validation, scoring (no redistribution, unavailable = 0), output comparison,
input-format inference, edge-case generation, complexity fitting, parsers for gcc / ASan / UBSan /
LSan / valgrind / cppcheck, originality, storage safety (IDs, roll numbers, uploads, immutability,
history, atomic writes, restart recovery), sandbox limits (timeout, segfault, memory, fork bomb,
output flood, file access, flags, missing Docker), the ten sample programs through the grading graph,
reproducibility, analyzer crash isolation, and the HTTP API end to end including report downloads,
resubmission history, teacher views and the originality flag.

## Grading policy (rules.json)

```json
{
  "problem": "add_two_integers",
  "time_limit_s": 1,
  "memory_limit_mb": 64,
  "input_spec": { "lines": [[{"name": "a", "type": "int", "min": -1000000000, "max": 1000000000},
                             {"name": "b", "type": "int", "min": -1000000000, "max": 1000000000}]],
                  "scale_fields": ["a", "b"] },
  "metrics": [
    { "name": "correctness", "analyzer": "io_tests", "weight": 0.20, "params": {} },
    { "name": "syntax", "analyzer": "compiler_warnings", "weight": 0.10,
      "params": { "flags": "-Wall -Wextra -Werror -std=c11" } }
  ]
}
```

Complete examples: [`samples/add_two_integers/rules.json`](samples/add_two_integers/rules.json) (the
brief's rule set) and [`samples/sort_numbers/rules.json`](samples/sort_numbers/rules.json) (with an
explicit input format and an O(n log n) bound).

| Key | Meaning |
|---|---|
| `metrics[]` | `name` (unique), `analyzer` (see below), `weight` (0..1, all weights sum to 1.00), `params` |
| `time_limit_s` | per-run CPU/wall limit, 0 < t <= 10 (default 1) |
| `memory_limit_mb` | per-run address-space limit, 8..1024 (default 64) |
| `compile_flags` | optional flags for the executed build (default `-O2 -std=c11`; `-Werror` is ignored here) |
| `input_spec` | optional input format: `lines` of fields `int` (min, max) or `int_list` (length = field or number); `size_field` (the input size) or `scale_fields` (ints whose value is the size). Without it the format is inferred from the accepted tests when they contain only integers |

Allowed gcc flags: `-W...`, `-std=c89..c23`/`gnu..`, `-O0..3/s/g`, `-g`, `-pedantic(-errors)`,
`-fsanitize=...`, `-fno-sanitize-recover`, `-fno-omit-frame-pointer`. Anything else (`-o`, `-I`,
`-fplugin`, linker options) is rejected.

## Analyzers

| Analyzer | What it does | Main params | Deterministic |
|---|---|---|---|
| `io_tests` | runs every accepted test, compares output ignoring trailing whitespace; failing input, expected, actual, explanation | `compare`, `float_tolerance`, `show_failures` | yes |
| `edge_case_runner` | (1) accepted tests in the requested categories, (2) format variants of accepted tests (final newline, extra spaces), (3) generated cases per theme run under UBSan (overflow, shifts, division by zero), (4) random counter-tests compared with the reference solution | `cases` (negatives, zero, int_overflow, boundary, duplicates, empty, single, sorted, reverse_sorted, large), `variants`, `random_tests` | yes |
| `compiler_warnings` | compiles with the rule's flags, categorises diagnostics by `-W` flag; `-Werror` warnings still count as warnings | `flags`, `penalty_per_warning` (0.1) | yes |
| `static_analysis` | lizard (cyclomatic complexity, function length) 60 % + cppcheck 40 %; unavailable cppcheck scores 0 and marks the metric `partial` | `max_cyclomatic`, `max_function_length`, `cppcheck_share` | yes |
| `function_split` | functions and helper functions vs. the rule | `min_functions`, `expect_helpers`, `max_main_length` | yes |
| `sanitizer_run` | ASan + UBSan + LSan on the tests after a sanitizer self-test, valgrind on a `-O0 -g` build; reports CPU time and peak memory per test (perf is blocked in the sandbox) | `flags`, `max_tests`, `valgrind`, `valgrind_tests` | yes |
| `complexity_estimator` | times the program at growing sizes (repeats, fastest kept), fits a + b·f(n) for 1, log n, n, n log n, n², n³, 2ⁿ; noise and non-monotonic data count as O(1); records fits, R², confidence | `required`, `sizes`, `repeats`, `partial_credit` | no (timing) |
| `llm_review` | Ollama, temperature 0, fixed seed, structured JSON: naming, layout, comments, organisation, maintainability | `model`, `temperature`, `seed` | no (LLM) |
| `similarity_flag` | Jaccard similarity of 6-token shingles after normalising identifiers, literals, comments and layout, against the other students' submissions and `Problem/corpus/*.c`; a flag asks for human review and **never** lowers the score | `flag_threshold`, `k`, `min_tokens` | yes |

**Result states.** `ok`; `partial` (a tool was missing, its share scores 0); `skipped` (because of the
program: compile failure or infinite loop, scores 0); `unavailable` (a tool or service is missing, no
score, counts 0); `error` (the analyzer crashed, counts 0). The grade is `100 · Σ weight · score`;
weights of unmeasured metrics are **not** redistributed, and the report lists them with the measured
`coverage` so the teacher can fix the tool and regrade.

## Reports

Every graded submission gets `report.json` and `report.txt` (student-safe) and `review.json`
(teacher-only: who a flagged submission resembles). The reports contain: student, roll number,
assignment, attempt, timestamps, grade, coverage and flags; first pass (compile flags and errors,
smoke run, static sanity); every metric with weight, score, contribution, status, feedback and
evidence; failing tests and counter-tests (input, expected, got, why); runtime (CPU, wall, peak memory);
complexity measurements and fit; memory findings; compiler and cppcheck diagnostics; readability
feedback; the originality flag; suggestions; tool versions; rules and tests hashes; the
reproducibility fingerprint; and the usefulness / limitations section. Example outputs for all sample
programs: run `python scripts/grade.py samples/add_two_integers --all`.

## Security

- Student code never runs on the host. The only execution path is `server/sandbox.py`, which refuses
  to run when the configured backend is unavailable; there is no fallback
- Container: `--network none`, `--read-only` root filesystem with a 128 MB `nosuid,nodev` tmpfs at
  `/tmp` (the only writable place, where the program is built and run), no host directories mounted,
  `--cap-drop ALL` plus SETUID/SETGID/KILL/DAC_OVERRIDE (needed to drop to `nobody` and clean up),
  `no-new-privileges`, `--memory 512m`, `--cpus 1`, `--pids-limit 128`, `nofile 256`, `--ipc none`,
  `--rm`; never `--privileged`; stopped containers are removed on timeout
- Inside: compiler and program run as `nobody` with RLIMIT_CPU, RLIMIT_AS (the rule's memory limit),
  RLIMIT_FSIZE (1 MiB output), RLIMIT_NPROC 16, no core dumps, a wall-clock timer that kills the
  process group, then every leftover `nobody` process; binaries are root-owned copies; expected
  outputs never enter the container
- Commands are argument lists (no shell); compiler flags are allow-listed on the server and again in the runner
- Uploads: `.c` only, UTF-8, no NUL bytes, at most 100 KB; roll numbers `[A-Za-z0-9_-]{1,32}`,
  upper-cased, Windows reserved names rejected; assignment IDs `ASG-[A-F0-9]{6}`; every path is built
  from validated IDs, so `..` cannot reach other folders; all files are written atomically
- Student endpoints only see published assignments and never return tests, rules, the reference
  solution or other students' data (originality matches are teacher-only)
- Not covered: there is no login, so anyone who can reach the server can use the teacher pages or read
  a report by guessing a roll number. Run it on a trusted network

## Data layout

```
data/Assignments/ASG-XXXXXX/
|-- meta.json                      id, title, status, rules hash, acceptance state
|-- Problem/
|   |-- problem.txt
|   |-- rules.json
|   |-- testcases.json             frozen once accepted
|   |-- reference.c                optional, teacher only
|   `-- corpus/*.c                 optional known solutions for the originality check
`-- Submissions/ROLL_NUMBER/
    |-- solution.c, info.json (name, attempt, sha256), status.json
    |-- report.json, report.txt, review.json
    `-- history/attempt_N/          every earlier attempt with its reports
```

## Usefulness and limitations

**Useful for**
1. **First-pass grading of large classes.** 300 sorting submissions are compiled, tested and scored
   unattended; the instructor only reads reports that are incomplete or flagged.
2. **Immediate, concrete feedback.** A student whose `a + b` overflows gets the input `2147483647 1`,
   the expected `2147483648` (from the reference solution) and the UBSan message, and can resubmit.
3. **Plagiarism / LLM-copy triage.** Two merge sorts with renamed variables and different layout score
   similarity 1.00 against a 0.85 threshold and are flagged; nobody is penalised automatically.
4. **Hiring screens / practice platforms.** Candidates are ranked by correctness, edge cases, memory
   safety and efficiency, with an explanation for every point lost.

**Limitations (each with a concrete wrong or unreliable verdict)**
1. **LLM-written expected outputs can be wrong.** In the existing assignment "ssss" the model wrote
   that the digit sum of `-1234` is `-10`; a correct program printing `10` fails that test. The teacher's
   review before Accept is the only check; a reference solution does not fix accepted tests.
2. **Tests cannot prove correctness.** A program that special-cases the exact hidden inputs passes every
   accepted test; without a reference solution the random counter-tests cannot catch it either.
3. **Timing-based complexity is an estimate.** For `sort_numbers` the qsort solution is reported as
   O(n) or O(n log n) depending on noise, because reading 32 000 numbers dominates; and an O(1) program
   measured on a busy machine could in principle be misread as O(log n). Fits and confidence are in the report.
4. **Similarity over- and under-flags.** Two honest six-line add-two-numbers programs are token-identical
   (so programs under 40 tokens are never flagged), while an LLM answer rewritten with a different loop
   structure scores around 0.4 and is not flagged. Copying from the web is only caught when the source
   is placed in `Problem/corpus/`.
5. **Tool availability changes the grade.** Without Ollama the readability share counts 0 and the grade
   is marked provisional; the report says so and the teacher can regrade later.
