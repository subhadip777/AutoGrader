# AutoGrader: A Rule-Driven Evaluator for C Programs

AutoGrader is an agent-based platform that grades student C programs according to rules the instructor defines. A teacher creates an assignment from a problem statement and a grading policy (JSON), the system generates test cases with a local LLM, the teacher reviews and accepts them, and the assignment is published for students.

The grading engine (sandboxed execution, per-metric analyzers, report generation) is under development. See [Project status](#project-status).

> Built as a course project on agentic systems. The core contract: **the same submission graded under the same rules always receives the same grade.**

## Features

**Working now**
- Teacher creates an assignment from a problem statement, a grading policy (`.json`) and a requested number of test cases
- Grading policy is validated on both client and server (known structure, weights sum to 1.00)
- Test cases are generated by a local LLM (Ollama) through a LangGraph workflow: batched generation, deduplication, validation, retry loop
- Teacher reviews the generated tests in a dedicated window and can **Regenerate** or **Accept**
- Accepted tests are saved to the assignment's folder; only then can the assignment be **Published**
- Published assignments are locked and appear as green tiles
- All data is stored as plain files, so every assignment is easy to inspect, copy and back up

**Planned**
- Student submission page (name, roll number, `.c` upload)
- Sandboxed compile and run under fixed time and memory limits (survives crashes and infinite loops)
- One analyzer per metric: correctness, compiler warnings, structure (cppcheck + lizard), modularity, edge cases, complexity estimation, memory safety (ASan/UBSan, valgrind), readability (LLM review), originality (similarity check)
- Weighted overall grade and per-student feedback with a failing input, the expected output and an explanation
- Reports saved per submission, tagged by roll number

## Tech stack

- **Backend:** Python 3.11+, FastAPI, Uvicorn
- **Agent workflows:** LangGraph, LangChain
- **LLM:** Ollama (local, offline), configurable model
- **Frontend:** plain HTML, CSS and JavaScript (no build step), served by FastAPI
- **Storage:** plain files on disk (JSON and text)
- **Planned tooling:** Docker sandbox, gcc, cppcheck, lizard, valgrind, ASan/UBSan, perf

## How it works

```
Browser (HTML/CSS/JS)
        |
        v
FastAPI  (single server, port 8000)
   |-- serves the frontend
   |-- /api/... endpoints
   '-- runs LangGraph workflows in-process
        |
        v
data/Assignments/...   (plain files)
```

**Teacher flow**
1. Create an assignment (title, problem statement, grading policy, number of tests).
2. Click **Validate test cases**. A review window opens and test generation starts in the background.
3. Read the generated inputs, expected outputs and explanations. Click **Regenerate** for a new set or **Accept**.
4. Click **Publish**. The assignment is locked.

**Test generation graph** (`backend/agents/testgen.py`)

`generate` (LLM, small batches, structured output) -> `validate` (drop empty, duplicate and oversized cases) -> repeat until enough tests exist or the attempt limit is reached.

## Getting started

### Prerequisites

- Python 3.11 or newer
- [Ollama](https://ollama.com) with a model pulled, for example `ollama pull qwen2.5:3b`
- Git

On machines with 8 GB RAM and no GPU, use a model of 3B parameters or smaller.

### Setup (Windows PowerShell)

```powershell
git clone <your-repo-url>
cd Autograder

copy .env.example .env      # then edit the model name if needed

python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements.txt
```

If PowerShell blocks activation, run once:
`Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned`

### Configuration (`.env`)

```
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=qwen2.5:3b
```

### Run

Make sure Ollama is running, then:

```powershell
cd backend
uvicorn server.main:app --reload --port 8000
```

Open <http://localhost:8000>. Interactive API docs are at <http://localhost:8000/docs>.

### Optional: inspect the agent in LangGraph Studio

```powershell
cd backend
langgraph dev
```

This is a debugging aid only and is not part of the running system.

## Grading policy format

The instructor supplies a JSON file. Weights must sum to 1.00. An example is in [`rules/add_two_integers.json`](rules/add_two_integers.json).

```json
{
  "problem": "add_two_integers",
  "time_limit_s": 1,
  "memory_limit_mb": 64,
  "metrics": [
    { "name": "correctness", "analyzer": "io_tests", "weight": 0.20, "params": {} },
    { "name": "syntax", "analyzer": "compiler_warnings", "weight": 0.10,
      "params": { "flags": "-Wall -Wextra -Werror -std=c11" } }
  ]
}
```

Rules live outside the source code, so adding or changing a metric does not require editing the agent.

## Data layout

Everything an assignment needs lives in one folder:

```
data/Assignments/
`-- ASG-XXXXXX/
    |-- meta.json            id, title, status, rules hash, acceptance state
    |-- Problem/
    |   |-- problem.txt
    |   |-- rules.json
    |   `-- testcases.json
    `-- Submissions/         (planned) one folder per roll number
```

`data/` is git-ignored because it will contain student code.

## API (current)

|---|---|---|

| GET | `/api/assignments` | List assignments |
| GET | `/api/assignments/{id}` | Get one assignment's metadata |
| POST | `/api/assignments/{id}/generate-tests` | Start background test generation |

## Design decisions

- **One server.** FastAPI serves both the API and the frontend, and calls LangGraph in-process. LangGraph is used as a library, not as a second server.
- **Tests are generated once, then frozen.** Generation may vary between runs, so tests are written to files at creation time and grading reads only those files. This protects reproducible grading.
- **Published assignments are immutable.** There is no versioning, so edits after publishing are refused to keep earlier grades valid.
- **Plain files over a database.** Easy to inspect, diff and back up, with no setup.
- **Safe paths.** File paths are built only from server-generated IDs that match a strict pattern, and files are written atomically.

## Known limitations

- Expected outputs are written by the LLM and are not independently verified. The teacher's review step is the only check, and small local models can make arithmetic mistakes.
- Test generation is slow on CPU-only machines (several minutes for 25 tests with a 3B model).
- There is no authentication. Anyone who can reach the server can act as a teacher or a student.
- Student code is not executed anywhere yet. The sandbox is the next major component and must be in place before real submissions are accepted.
- Statements are read as text. PDF problem statements are not yet supported.

## Roadmap

1. Sandbox runner (Docker, no network, time and memory limits)
2. Grading graph: first-pass checks, then analyzers one at a time
3. Student UI: assignment list, submission, report view
4. Remaining analyzers: complexity, sanitizers, originality, LLM readability
5. PDF statement support
6. Usefulness and limitations analysis for the final report
